# Compact run outcome

The prepared Python outcome remains the original private evidence artifact. The
PHP DTOs under `app/DTOs/AuditRun` provide a read-only projection; they do not change
the agent loop, write database rows or replace the original JSON.

```php
$outcome = $auditRun->getOutcomeSummary();
$array = $outcome?->toArray();
$json = json_encode($outcome, JSON_THROW_ON_ERROR | JSON_UNESCAPED_SLASHES);
```

`RunOutcome::fromArray($rawOutcome)` also works without Eloquent. `getOutcome()`
continues to expose the original associative array, now decoded recursively and
with JSON errors reported. Both model accessors return null when the output file
does not exist. Invalid input/schema/status is not presented as an empty success.
The existing `app:test` command now dumps the compact array.

## Retained data

- Run/source identity, source hash and input artifact IDs, status, reason,
  termination reason and whether coverage is complete.
- `AreaOutcome` objects: pass and area keys, title/origin, normalized execution
  status, reason, source paths, next check and the bounded Reader checkpoint.
- `LeadOutcome` objects: pass-qualified runtime identity, originating area/output,
  status/lifecycle, title, original severity/confidence/classification, description,
  one final investigator narrative, distinct stop reason, recommendation, source
  locations and evidence references.
- Deferred Reader proposals use the same lead DTO shape in a separate
  `deferred_leads` list, with pending/not-admitted status and their admission reason.
  They are not presented as investigated findings or rejected vulnerabilities.
- Essential usage: model requests, input/output tokens, economic points and cost
  fields when available. Unknown provider cost remains null, with its accounting
  completeness flag; it is not treated as zero or replaced by an estimate.
- Compact blockers/errors and summary counts. Explicitly rejected, closed,
  duplicate or superseded lead rows are counted rather than copied into the main
  lead list. Technical blocked/inconclusive lead rows remain when present in the
  authoritative finding buckets.

## Removed duplication

Large source snippets, HTTP bodies, request credentials, tool logs/events, pricing
catalogs, individual budget grants, intermediate handoffs and repeated copies of
the final narrative are not embedded in the projection. The narrative itself is
not truncated or regenerated by a model. Locations retain file/line ranges.
HTTP evidence keeps request/response IDs, and source evidence keeps reference IDs;
the tool journal filename is preserved. These refer back to the original outcome
and its neighboring journals, within the corresponding pass. They are not a
standalone exploit reproduction package.

The normalizer uses the aggregated finding lists once. Area coverage, HTTP
reference resolution and deferred Reader proposals come from each pass report,
where the current legacy runtime stores them. Pass IDs remain explicit to prevent
collisions between local runtime IDs across passes. Area counts describe the
retained pass-area executions, not unique definitions across multiple passes.

Reader `finished` alone does not mean complete coverage. Explicitly closed areas
become completed; queued/not-started areas remain pending; terminal-run active
areas become partial; explicitly scoped Reader failures become failed. An active
area in a live run remains running. The normalizer does not infer vulnerability
severity, confirmation or area completion from prose or from the global run status.

`not_admitted_*` Reader outputs are retained separately. Other nonaccepted Reader
outputs, including invalid source references and duplicates, are counted as
discarded outputs and remain available in the raw JSON.

## Verified real run

Run `01m57v22vtn1bxydvrmk6drvcc` produced a 900,833-byte outcome. Its compact JSON is
26,089 bytes (about 97% smaller), retaining three confirmed leads, two partial
areas, eight pending areas and two deferred Reader proposals. No areas completed
and no final lead rows were rejected. One invalid Reader output is counted as
discarded rather than being presented as a finding.

Verification read the existing outcome without modifying it or writing database
rows. Additional offline fixtures covered direct and aggregated reports,
pass-qualified identities, blocked versus rejected leads, active/failed/completed
areas, missing reports on failed runs and serialization. No agents were launched.

`OutcomeService::persist` now imports the compact DTO into `audit_runs.outcome`
and projects areas/leads through dedicated Actions. `audit:run` calls it for a
validated terminal outcome. Source snippets, HTTP details and optional journal
previews are added only during presentation. The DTO is not written as an extra
file in each run directory; the original Python JSON remains on disk. The historical
run used above has not been imported automatically.
